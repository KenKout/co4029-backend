# NFR-2.1 Peak-Load Results — 2026-09-26

Scenario: `07_nfr_peak` — composite profile mô phỏng lớp học đang diễn ra:
80% VUs browse (bootstrap + dashboard + curriculum + notification polling),
20% VUs làm quiz đầy đủ (start → answers → heartbeats → integrity → submit).
200 synthetic students (`k6-loadtest-NNN@abridgeai.local`), mỗi VU một user.
Target: `https://abridgeai.tech` (production path, TLS). Think time 2s.
Mỗi mức chạy 3 phút sustained, matrix 1× / 2× / 4× mức NFR-2.1 (50 users).

Đợt chạy gồm **hai cấu hình** — trước và sau remediation:

* **Config A (trước)**: 1 Uvicorn worker (cấu hình deploy cũ)
* **Config B (sau)**: 4 Uvicorn workers (`--workers 4` trong
  `ecosystem.config.cjs`, PM2 reload + `pm2 save` — thay đổi vĩnh viễn)

## Key findings

1. **Config A bottleneck = chính process Uvicorn đơn**: telemetry trong run 4×
   cho thấy uvicorn 110% CPU (~1 core) trong khi server idle 71.8% và
   PostgreSQL 10% CPU. Máy và DB còn nhiều dư địa — thiếu worker.
2. **4 workers lifted ceiling ~3× (35→111 RPS), gần tuyến tính theo worker**,
   và đưa mức NFR (50 VUs) vào vùng hoàn toàn thoải mái: p50 73ms, p95 464ms,
   0% lỗi — vượt cả ngưỡng NFR-2.2 (avg < 0.5s) lẫn NFR-1.4 (< 2s).
3. **Config B bottleneck mới = PostgreSQL max_connections**: ở 4× (200 VUs),
   lần đầu xuất hiện 0.55% lỗi — toàn bộ là HTTP 500 với
   `psycopg.OperationalError: connection to server failed: FATAL` ở
   127.0.0.1:5433 khi 4 workers × connection pool vắt kiệt giới hạn
   `max_connections` của PG. Bước remediation tiếp theo (nếu cần scale nữa):
   PgBouncer hoặc tăng `max_connections` / tinh chỉnh pool size mỗi worker.
4. **0% lỗi ở mọi mức ngoại trừ 4× Config B (0.55% < 1% threshold)** —
   degradation duyên dáng, không crash (thỏa tiêu chí TC-NFR-2.1 "excess
   requests are handled without crashing core services" tới 4× NFR).
5. **Endpoint chậm nhất dưới tải** vẫn là các aggregate per-user:
   `GET /me/sr-dashboard-summary` (p50 110ms @1× 4-workers nhưng 2.23s khi
   saturation), `POST /attempts/{id}/submit` (grading + SM-2 in-transaction
   + notifications), `GET /me/cards-due`.
6. So với kì trước (single-endpoint GET, 136–431 RPS): profile mixed per-user
   + writes này thực tế và nặng hơn hẳn — số liệu hai kì không so trực tiếp
   được, nhưng cùng methodology LAN/TLS và cùng deployment.

## Verdict against the NFRs (Config B — 4 workers, cấu hình hiện tại)

* **NFR-2.1 (50 concurrent active users, no degradation)** — **PASS, evidenced**:
  ở đúng 50 VUs liên tục (pacing 2s — gắt hơn pacing con người thật), p95
  464ms, 0% lỗi, max 1.67s. NFR level nằm ở ~45% capacity (111 RPS ceiling)
  → headroom ~2.2× trước khi latency bắt đầu degrade ở 2×, ~4× trước khi
  xuất hiện lỗi đầu tiên.
* **NFR-1.4 (dashboard < 2s average)** — **PASS** @1× (p50 73ms, max 1.67s);
  border @2×; FAIL @4×.
* **NFR-2.2 (avg query < 0.5s)** — **PASS** @1× (toàn bộ endpoint p50 < 400ms,
  avg well under 500ms); border @2×; FAIL @4×.
* **TC-NFR-2.1 (excess requests không crash)** — **PASS** tới 4×: chỉ queueing
  + 0.55% HTTP 500 (PG connection ceiling) ở 200 VUs, không crash tiến trình
  nào, recovery ngay khi giảm tải.
